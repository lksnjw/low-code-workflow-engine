# Validation gate specification

## Scope and the two validators

The backend has two distinct validators. `WorkflowValidator` is the preliminary schema/semantic validator used to parse ordinary HTTP inputs and produce the older `ValidationResult`; it is not the registry gate. `RegistryValidator` is the full deterministic gate: it resolves tools and enabled governance rules, emits a `CandidateValidationResult`, issues a signed `ValidationToken` only after a pass, re-evaluates deferred rules at dispatch, and mints the otherwise unconstructable dispatch capability. [backend/internal/core/validator/schema_check.go:11-56](../../backend/internal/core/validator/schema_check.go) [backend/internal/core/validator/registry_validator.go:47-106](../../backend/internal/core/validator/registry_validator.go)

The normal write/run paths first use `WorkflowValidator.ValidateYAML`, then call the full gate through the handler helper. A preliminary pass is therefore necessary but insufficient for persistence or execution. [backend/internal/api/handlers/workflow_handler.go:68-117](../../backend/internal/api/handlers/workflow_handler.go) [backend/internal/api/handlers/handler.go:144-155](../../backend/internal/api/handlers/handler.go)

## 4.2 Parsing

The preliminary parser removes a surrounding Markdown code fence, calls `yaml.Unmarshal`, and therefore does not reject unknown fields or a trailing second document. It returns `parse workflow yaml: <decoder error>` on syntax/type failure. [backend/pkg/parser/yaml_util.go:13-20](../../backend/pkg/parser/yaml_util.go) [backend/pkg/parser/yaml_util.go:32-39](../../backend/pkg/parser/yaml_util.go)

The full gate uses this exact strict algorithm:

1. Remove a surrounding Markdown fence with `parser.StripMarkdownFence`.
2. Create a `yaml.v3.Decoder` and enable `KnownFields(true)`.
3. Decode exactly one `WorkflowBlueprint`; syntax errors, type mismatches, and any mapping key not represented by a YAML-tagged struct field reject with `parse workflow yaml: <error>`.
4. Decode once more into `interface{}`. Only `io.EOF` is success; a successful second decode rejects with `parse workflow yaml: multiple YAML documents are not allowed`, and any other error is wrapped as a parse error. [backend/internal/core/validator/registry_validator.go:1029-1045](../../backend/internal/core/validator/registry_validator.go)

Empty YAML can decode to the zero blueprint, but it subsequently fails validation tags; strict parsing itself does not require nonempty input. [backend/internal/core/validator/registry_validator.go:147-160](../../backend/internal/core/validator/registry_validator.go)

## 4.3 Full-gate checks in exact order

The result begins with every category flag true, empty error/warning/rule/deferred lists, current tool/rule versions, risk `low`, and empty maps. Only parse failure short-circuits the plan gate; every later phase accumulates errors and finishes once at the end. [backend/internal/core/validator/registry_validator.go:127-155](../../backend/internal/core/validator/registry_validator.go)

1. **Strict parse.** Failure sets `SchemaOK=false`, appends `YAML_PARSE_ERROR: <error>`, calculates the score/pass, and returns immediately. [backend/internal/core/validator/registry_validator.go:147-153](../../backend/internal/core/validator/registry_validator.go)
2. **Struct tags.** Validate the whole blueprint with `go-playground/validator`; any failure sets `SchemaOK=false` and appends `SCHEMA_INVALID: YAML failed schema validation: <validation error>`. [backend/internal/core/validator/registry_validator.go:157-160](../../backend/internal/core/validator/registry_validator.go)
3. **Generated-candidate description invariant.** Trimmed blank description sets `SchemaOK=false` and `SCHEMA_DESCRIPTION_REQUIRED`. This applies to all full-gate calls despite the wording. [backend/internal/core/validator/registry_validator.go:161-164](../../backend/internal/core/validator/registry_validator.go)
4. **Step scan, in YAML order.** Analysis steps take the analysis branch and skip tool checks. A non-analysis/non-tool effective kind sets `SchemaOK=false` and `STEP_KIND_INVALID`. [backend/internal/core/validator/registry_validator.go:166-177](../../backend/internal/core/validator/registry_validator.go)
5. **Analysis structure.** Require instruction; validate output schema; reject negative input limits; require `input` to be exactly a `{{priorStep.output}}` or `{{priorStep.output.path}}` expression whose step ID occurs earlier. Violations use `ANALYSIS_INSTRUCTION_REQUIRED`, `ANALYSIS_OUTPUT_SCHEMA_INVALID`, `ANALYSIS_INPUT_LIMIT_INVALID`, `ANALYSIS_INPUT_INVALID`, or `ANALYSIS_INPUT_SOURCE_UNDECLARED`. Then every enabled data-confidentiality rule is parsed; malformed conditions fail policy closed, valid ones become deferred and may reject a forbidden explicit field path. [backend/internal/core/validator/analysis_validation.go:13-65](../../backend/internal/core/validator/analysis_validation.go)
6. **Tool identity.** Trim action, index its lowercase occurrence for later order rules, and perform an in-memory exact normalized name/MCP-name lookup. Missing tool sets `ToolValidityOK=false`, records failed rule `GLOBAL-SAFETY-001`, and skips the rest of that step. [backend/internal/core/validator/registry_validator.go:178-186](../../backend/internal/core/validator/registry_validator.go) [backend/internal/core/registry/tool_registry.go:24-35](../../backend/internal/core/registry/tool_registry.go)
7. **Tool status.** Empty or `active_mcp_schema_present` passes. `mock_endpoint_available_schema_missing`, `recommended_future_capability`, or any other status sets tool validity false and records `CAP-GAP-001` with status-specific text. [backend/internal/core/validator/registry_validator.go:205-218](../../backend/internal/core/validator/registry_validator.go)
8. **Registry-required parameters.** Each `RequiredParameters` key must exist and not be nil/blank/`<nil>`/case-insensitive `null`; failure sets parameters false and adds `MISSING_PARAMETER`. Other zero values such as numeric zero and `false` are nonempty. [backend/internal/core/validator/registry_validator.go:221-231](../../backend/internal/core/validator/registry_validator.go) [backend/internal/core/validator/registry_validator.go:678-687](../../backend/internal/core/validator/registry_validator.go)
9. **Tool role.** Empty allowed-role list permits all. Role normalization trims, lowercases, converts spaces/hyphens to underscore, and aliases `platform_admin` to `admin`; `admin` is an unconditional tool-role bypass. Otherwise normalized role must equal an allowed role. Failure sets RBAC false and adds `RBAC_DENIED`. [backend/internal/core/validator/registry_validator.go:234-240](../../backend/internal/core/validator/registry_validator.go) [backend/internal/core/validator/registry_validator.go:751-785](../../backend/internal/core/validator/registry_validator.go)
10. **Literal credential-key scan.** Recursively traverse maps/slices. A key is sensitive when its trimmed lowercase form contains `password`, `token`, `api_key`, `apikey`, `secret`, `authorization`, `auth_header`, or `private_key`. First hit sets policy false and failed rule `GLOBAL-SAFETY-002`; values are not pattern-scanned. [backend/internal/core/validator/registry_validator.go:193-197](../../backend/internal/core/validator/registry_validator.go) [backend/internal/core/validator/registry_validator.go:689-748](../../backend/internal/core/validator/registry_validator.go)
11. **Sensitive-template deferral.** For each parameter containing an unresolved template at any nested depth, record applicable enabled sensitivity rules for dispatch. [backend/internal/core/validator/registry_validator.go:594-610](../../backend/internal/core/validator/registry_validator.go)
12. **Enabled rule loop.** Iterate the registry snapshot in stored order. A family classified `NO_EVALUATOR` fails closed before scope matching. Otherwise apply deterministic scope matching and its family evaluator; errors accumulate rather than short-circuiting. [backend/internal/core/validator/registry_validator.go:242-275](../../backend/internal/core/validator/registry_validator.go)
13. **Finish.** Sort/deduplicate failed-rule IDs; score flags with weights schema/tool/parameters `0.20` each, RBAC/policy `0.15` each, order/risk `0.05` each, rounded to two decimals. `Passed` requires all seven flags and zero errors. [backend/internal/core/validator/registry_validator.go:646-675](../../backend/internal/core/validator/registry_validator.go)
14. **Issue and audit.** A pass creates/signs the token; either outcome writes a gate audit. [backend/internal/core/validator/registry_validator.go:79-106](../../backend/internal/core/validator/registry_validator.go)

Warnings are initialized but no full registry-gate evaluator appends one; therefore current full-gate warnings remain empty. [backend/internal/core/validator/registry_validator.go:127-145](../../backend/internal/core/validator/registry_validator.go)

## 4.4 Deterministic rule loading and scope

The evaluator obtains a copy-like slice of enabled in-memory rules by scanning registry order and checking only `Enabled`; it performs no semantic/vector search and no network call. Tool lookup is an in-memory map lookup under `RWMutex`. The validator package imports registry, models, repository, parser, YAML/validation and standard libraries—no HTTP/search client. [backend/internal/core/registry/rule_registry.go:53-60](../../backend/internal/core/registry/rule_registry.go) [backend/internal/core/registry/tool_registry.go:69-80](../../backend/internal/core/registry/tool_registry.go) [backend/internal/core/validator/registry_validator.go:3-22](../../backend/internal/core/validator/registry_validator.go)

`ruleAppliesToCandidate` is the exact scope predicate, evaluated after the no-evaluator fail-closed check:

1. If there are no used tools and the rule ID is not one of the hard-coded mandatory global IDs, reject scope.
2. If `applies_to_roles` is nonempty, normalized user role must equal one listed role; unlike tool authorization, there is no admin bypass in this predicate.
3. If `applies_to_tools` is nonempty, at least one used tool must case-insensitively equal an item by tool name, tool ID, or MCP tool name. This returns immediately and does not additionally require domain matching.
4. Otherwise, a global domain or `GLOBAL-` ID applies only when it is a hard-coded mandatory global rule or a qualifying `risk_escalation`/`audit` rule. Risk qualification compares the candidate maximum risk with condition value; missing/null value defaults to `high`.
5. Otherwise, a nonblank domain applies if it equals a used tool's module or ERP system, or is a lowercase substring of ERP system.
6. Otherwise it does not apply. [backend/internal/core/validator/registry_validator.go:787-868](../../backend/internal/core/validator/registry_validator.go)

Mandatory global IDs are exactly `GLOBAL-SAFETY-001`, `GLOBAL-SAFETY-002`, `GLOBAL-SAFETY-003`, `GLOBAL-AUDIT-001`, `GLOBAL-SAFETY-008`, `GLOBAL-SAFETY-009`, `GLOBAL-SAFETY-010`, `GLOBAL-SCORING-008`, `GLOBAL-SCORING-009`, and `GLOBAL-SCORING-010`. [backend/internal/core/validator/registry_validator.go:828-844](../../backend/internal/core/validator/registry_validator.go)

## 4.6 Deferred checks

`containsUnresolvedTemplate` recursively visits strings, maps, and lists. A string is “unresolved” whenever it contains both `{{` and `}}` anywhere; syntax, balance, and supported variable grammar are not checked here. [backend/internal/core/validator/registry_validator.go:720-738](../../backend/internal/core/validator/registry_validator.go)

Deferral records `{step_index,param_key,rule_ids}`. Checks with the same step/key are merged, duplicate rule IDs suppressed and the per-check IDs sorted; new check records retain discovery order. [backend/internal/core/validator/registry_validator.go:628-644](../../backend/internal/core/validator/registry_validator.go)

At dispatch, only checks whose `step_index` matches are evaluated in token order. A missing/disabled rule, no-evaluator family, unevaluable family/shape, or failed resolved evaluation stops at the first violation and prevents capability minting. The audit stores checked rule IDs, failed rule/key/reason, but not the unredacted value. [backend/internal/core/validator/registry_validator.go:444-522](../../backend/internal/core/validator/registry_validator.go)

## 4.7 Validation token

The token is `{workflow_content_hash,registry_hash,passed_at,deferred_checks}` in JSON; `Proof` is deliberately `json:"-"`. The workflow hash is SHA-256 over the exact raw string bytes—Markdown fences, whitespace, and line endings therefore matter. The registry hash is SHA-256 over exact tool-version bytes, one `0x00`, then rule-version bytes. Both visible hashes use lowercase hexadecimal with `sha256:` prefix. [backend/internal/models/validation_token.go:5-20](../../backend/internal/models/validation_token.go) [backend/internal/core/validator/registry_validator.go:1047-1056](../../backend/internal/core/validator/registry_validator.go)

Signing JSON-marshals a fixed field-order struct containing those four fields, including Go/RFC3339 time serialization and the deferred-check slice order. HMAC-SHA-256 uses the validator instance's random 32-byte key; proof is lowercase hex without a prefix. Marshal failure panics. Verification reconstructs this payload, hex-decodes provided/expected proofs, and performs constant-time equality. No expiry is enforced and `PassedAt` is only integrity-bound evidence. [backend/internal/core/validator/registry_validator.go:1096-1115](../../backend/internal/core/validator/registry_validator.go) [backend/internal/core/validator/registry_validator.go:109-125](../../backend/internal/core/validator/registry_validator.go)

## 4.8 Dispatch capability and tool boundary

`DispatchCapability` contains six unexported fields: proof `{minted bool}`, workflow hash, registry hash, step index, action, and resolved-parameter hash. The zero value is unusable. `IsUsable` requires minted proof, nonblank hashes/action/parameter hash, and a nonnegative index. External packages can name the exported type and call getters, but cannot name/populate its unexported proof or other fields in Go source. [backend/internal/core/validator/dispatch_capability.go:13-45](../../backend/internal/core/validator/dispatch_capability.go)

Only `mintDispatchCapability` constructs a usable value. It re-verifies token proof/current registry/index, JSON-marshals resolved parameters (the encoder deterministically sorts string map keys), hashes those bytes, and binds the action at the validated index. [backend/internal/core/validator/dispatch_capability.go:47-85](../../backend/internal/core/validator/dispatch_capability.go)

Before an MCP request is sent, the tool boundary requires `IsUsable`, requires capability action to equal the client tool name, JSON-serializes the actual parameter map, and requires SHA-256 of those exact outgoing parameter bytes to equal the capability hash. Only then does it construct/send the bridge request. [backend/internal/tools/mcp_client.go:53-83](../../backend/internal/tools/mcp_client.go)

The `ignore`-tagged compile-fail witness attempts to populate `proof` and `dispatchProof` from package `tools`; including it makes compilation fail, while the default build excludes it. [backend/internal/tools/dispatch_capability_compile_fail.go:1-12](../../backend/internal/tools/dispatch_capability_compile_fail.go)
