# 3. HTTP API contract

## Path and notation

`B` below means `Config.APIBasePath`, whose default is `/api`; `/healthz` and `/ws/*` are outside `B`. [backend/internal/config/config.go:113-121](../../backend/internal/config/config.go) [backend/internal/api/routes/routes.go:12-19](../../backend/internal/api/routes/routes.go)

`OK(data, message, meta)` means HTTP JSON `{ "success": true, "data": data, "message": message, "meta": meta }`; blank success messages become `"OK"`. `FAIL(status, message, meta)` means status plus `{ "success": false, "data": null, "message": message, "meta": meta }`; blank failure messages become `"Request failed"`. [backend/internal/models/api.go:5-36](../../backend/internal/models/api.go)

When a handler returns `fiber.NewError(status,message)`, the application error handler converts it to `FAIL(status,message,null)`. An unrecognized error becomes `FAIL(500,"Internal server error",null)`. [backend/cmd/server/main.go:206-218](../../backend/cmd/server/main.go)

Unless a row says otherwise, success is HTTP 200 JSON. `Body map` means a JSON object decoded to `map[string]interface{}`; malformed JSON is `FAIL(400,"Invalid request body",null)`. [backend/internal/api/handlers/handler.go:99-104](../../backend/internal/api/handlers/handler.go) [backend/internal/api/handlers/handler.go:272-278](../../backend/internal/api/handlers/handler.go)

## Middleware chains and shared errors

Every route is preceded, in this order, by: (1) CORS, allowing configured origins, headers `Origin, Content-Type, Accept, Authorization`, methods `GET,POST,PATCH,PUT,DELETE,OPTIONS`, and credentials; (2) request logging after downstream processing, recording method, path, response status, latency, and IP; (3) the persistence-failure guard. [backend/cmd/server/main.go:220-229](../../backend/cmd/server/main.go) [backend/internal/api/middlewares/logger.go:10-23](../../backend/internal/api/middlewares/logger.go)

For POST/PUT/PATCH/DELETE with durable storage, the persistence guard serializes mutating requests. If storage is already unhealthy and a 250 ms probe fails, or if the request advances the persistence-failure generation, it returns `FAIL(503,"Storage persistence is unavailable; no mutation was committed and the request can be retried",null)`. Memory-mode and GET requests pass through. This shared error is denoted `PERSIST`. [backend/internal/api/middlewares/persistence.go:13-63](../../backend/internal/api/middlewares/persistence.go)

Chain names used per row:

- `public`: global middleware, then handler.
- `auth-rate`: global middleware, then a process-local fixed-window limiter of 10 requests per IP+path per minute, then handler. The 11th request sets `Retry-After` and returns `FAIL(429,"Too many authentication attempts; try again later",null)`. [backend/internal/api/routes/routes.go:19-28](../../backend/internal/api/routes/routes.go) [backend/internal/api/middlewares/rate_limit.go:17-58](../../backend/internal/api/middlewares/rate_limit.go)
- `protected`: global middleware → `Auth` → `RequireUser` → handler. `Auth` accepts only an `Authorization: Bearer <JWT>` header except `/ws/*`, where query `token` is a fallback; it requires HS256 and nonblank string `sub`. It returns respectively `FAIL(401,"Missing access token",null)`, `FAIL(401,"Invalid or expired access token",null)`, `FAIL(401,"Invalid token claims",null)`, or `FAIL(401,"Invalid token subject",null)`. `RequireUser` then returns `FAIL(401,"Authenticated user no longer exists",null)` for a missing account or `FAIL(403,"User account is not active",null)` for a non-active account. [backend/internal/api/middlewares/auth.go:13-46](../../backend/internal/api/middlewares/auth.go) [backend/internal/api/handlers/handler.go:119-131](../../backend/internal/api/handlers/handler.go)
- `protected + perm(X)`: protected chain, then exact-permission middleware. Failure is `FAIL(403,"Permission denied",{"required":"X"})`.
- `protected + any(A,B)`: protected chain, then any-permission middleware. Failure is `FAIL(403,"Permission denied",{"requiredAny":["A","B"]})`. [backend/internal/api/middlewares/rbac.go:8-31](../../backend/internal/api/middlewares/rbac.go)

The route aliases are exact: `workflowRead=workflow:read`, `workflowWrite=workflow:write`, `workflowRun=workflow:run`, `workflowReadAny=any(workflow:read,workflow:read_own)`, `workflowRunAny=any(workflow:run,workflow:run_own)`, `executionReadAny=any(workflow:read,execution:read_own)`, `chatReadAny=any(workflow:read,chat:use)`, `chatWriteAny=any(workflow:write,chat:use)`, `settingsManage=settings:manage`, `providerManage=provider:manage`, `registryRead=registry:read`, `registryWrite=registry:write`, `userManage=user:manage`, and `auditRead=audit:read`. [backend/internal/api/routes/routes.go:30-44](../../backend/internal/api/routes/routes.go)

At resource scope, `workflow:read_own` permits only owner/assignee workflows, `workflow:run_own` permits only owner/assignee execution, `execution:read_own` permits only executions whose `StartedBy.ID` is the caller, and `chat:use` permits only caller-owned sessions. Unauthorized scoped resources are generally hidden as 404 by handlers. [backend/internal/api/handlers/scope_helper.go:21-62](../../backend/internal/api/handlers/scope_helper.go)

## Shared response and error contract recap

Except for successful CSV audit export, successful upload download, WebSocket traffic, and framework-generated upgrade failures, HTTP handlers return `APIResponse`: `success` is boolean, `data` is the payload or `null`, `message` is a human-readable string, and `meta` is an object or `null`. Success is normally `OK(data,message,meta)`; failures are `FAIL(status,message,meta)`. [backend/internal/models/api.go:5-26](../../backend/internal/models/api.go)

Unhandled `fiber.Error` values are normalized by the app-level error handler; other returned errors become status 500, all with `{success:false,data:null,message,meta:null}`. Thus clients must key behavior on HTTP status and structured `meta` when present, not on message text alone. [backend/cmd/server/main.go:206-218](../../backend/cmd/server/main.go)

Mutation methods are subject to `PersistenceFailureGuard` before handler execution. With durable storage, each POST/PUT/PATCH/DELETE is serialized under the persistence mutex and flushed after the handler returns; once persistence health is degraded, subsequent mutations return 503. Because flush occurs after the handler and response body have been built, a flush failure can replace the status/response while the in-memory mutation has already happened. [backend/internal/api/middlewares/persistence.go:13-63](../../backend/internal/api/middlewares/persistence.go)
