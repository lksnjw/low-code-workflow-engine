## Architecture summary

`cmd/server` constructs a Fiber API over a single synchronized repository aggregate, a strict runtime tool/rule registry, deterministic validation gate, sequential synchronous runner, MCP tool transport, optional LLM synthesis/analysis, semantic retrieval, and either memory-only or encrypted PostgreSQL snapshot storage. Routes authenticate current users and derive permissions from current role state; workflow mutations and runs pass preliminary parsing and then the registry gate; the runner verifies the signed content/registry token again, resolves each step, and requires a validator-minted parameter-bound capability immediately before tool dispatch. [backend/cmd/server/main.go:31-235](../../backend/cmd/server/main.go) [backend/internal/api/routes/routes.go:12-215](../../backend/internal/api/routes/routes.go) [backend/internal/core/runner/executor.go:49-170](../../backend/internal/core/runner/executor.go)

The effective dependency direction is server → routes → handlers → core/repository/tools, with repository → storage. It is acyclic but not a strict onion: runner imports concrete tools, validator imports concrete repository for audit, and config imports registry. [backend/internal/core/runner/executor.go:9-16](../../backend/internal/core/runner/executor.go) [backend/internal/core/validator/registry_validator.go:16-20](../../backend/internal/core/validator/registry_validator.go) [backend/internal/config/runtime_registry.go:3-12](../../backend/internal/config/runtime_registry.go)

## Request lifecycle

1. Fiber applies global CORS, request logging, and persistence-failure guard. Durable mutation requests are serialized and refused when persistence is degraded. [backend/cmd/server/main.go:220-229](../../backend/cmd/server/main.go) [backend/internal/api/middlewares/persistence.go:17-63](../../backend/internal/api/middlewares/persistence.go)
2. Public routes proceed directly. Protected routes parse an HS256 bearer JWT, require a string subject, reload the current user, and require active status. [backend/internal/api/routes/routes.go:16-30](../../backend/internal/api/routes/routes.go) [backend/internal/api/middlewares/auth.go:13-45](../../backend/internal/api/middlewares/auth.go) [backend/internal/api/handlers/handler.go:119-131](../../backend/internal/api/handlers/handler.go)
3. Route-specific middleware compares exact effective permission strings. Effective permissions are freshly derived as role permissions plus additive overrides; own/all handlers then apply record scope. [backend/internal/api/middlewares/rbac.go:8-30](../../backend/internal/api/middlewares/rbac.go) [backend/internal/repository/memory.go:134-188](../../backend/internal/repository/memory.go) [backend/internal/api/handlers/scope_helper.go:21-62](../../backend/internal/api/handlers/scope_helper.go)
4. The handler parses path/query/body and performs endpoint-specific checks. Workflow definition mutations first run preliminary schema/semantic validation, then the full registry gate; no successful full-gate token means no production persistence/dispatch. [backend/internal/api/handlers/handler.go:99-103](../../backend/internal/api/handlers/handler.go) [backend/internal/api/handlers/workflow_handler.go:68-117](../../backend/internal/api/handlers/workflow_handler.go)
5. The full gate strict-parses one YAML document, applies struct and step checks, resolves registered tools, performs literal safety/RBAC checks, deterministically scopes/evaluates every enabled rule, records deferred checks, calculates the result, signs a token only on pass, and audits either decision. [backend/internal/core/validator/registry_validator.go:79-106](../../backend/internal/core/validator/registry_validator.go) [backend/internal/core/validator/registry_validator.go:127-275](../../backend/internal/core/validator/registry_validator.go)
6. For execution, the handler stores a `RUNNING` record and calls the runner synchronously. Runner re-verifies token proof, exact workflow hash, and current registry hash before strict reparsing/state initialization. [backend/internal/api/handlers/execute_handler.go:63-75](../../backend/internal/api/handlers/execute_handler.go) [backend/internal/core/runner/executor.go:49-76](../../backend/internal/core/runner/executor.go)
7. Each tool step resolves variables, adds `_action`, re-evaluates resolved/deferred policy, mints a capability, resolves a tool, and calls it. MCP verifies capability usability/action and hashes the exact outgoing parameter JSON before any network request. Analysis steps instead resolve/limit/egress-check model input and require schema-valid JSON output, with one schema-correction retry. [backend/internal/core/runner/executor.go:78-167](../../backend/internal/core/runner/executor.go) [backend/internal/tools/mcp_client.go:62-120](../../backend/internal/tools/mcp_client.go) [backend/internal/core/runner/analysis.go:48-115](../../backend/internal/core/runner/analysis.go)
8. On completion/failure, the handler derives redacted partial/final outputs, classifies the error, optionally attempts one transient-failure repair without re-execution, and atomically stores the final execution/log/timeline/audit batch. [backend/internal/api/handlers/execute_handler.go:75-183](../../backend/internal/api/handlers/execute_handler.go)
9. A handler normally returns the shared API envelope. In PostgreSQL mode, every store write synchronously serializes, AES-GCM-encrypts, and upserts the complete versioned aggregate; a failed save rolls memory back and the middleware returns persistence failure. [backend/internal/models/api.go:5-26](../../backend/internal/models/api.go) [backend/internal/repository/persistent_store.go:52-102](../../backend/internal/repository/persistent_store.go) [backend/internal/storage/codec.go:15-80](../../backend/internal/storage/codec.go)
